# Distribution and Releases

## Requirements

| ID          | Requirement                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| ----------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| LP-SPEC-010 | The repository MUST publish the twelve packages listed in `scripts/package-catalog.mjs` under their existing `@lapis-notes/*` names and runtime IDs, beginning at independently versioned `0.1.0` versions without Changesets fixed or linked groups.                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| LP-SPEC-011 | Every published manifest MUST use registry semver ranges and MUST export its plugin entry, public types, `manifest.json`, and `styles.css`; package entrypoints MUST resolve packaged metadata through package self-references or another npm-package-contained path and MUST NOT depend on the source workspace layout. Published manifests MUST declare every `@lapis-notes/*` host package as a peer dependency and MUST NOT contain `workspace:`, `link:`, `file:`, or machine-local dependency paths. A plugin that imports another workspace plugin's public exports MUST also declare that peer as a semver development dependency so clean checks build the provider first without changing runtime ownership. |
| LP-SPEC-012 | One source commit and package version MUST produce both an npm tarball and a deterministic `<plugin-id>-<version>.lapis-plugin` ZIP-compatible archive with its SHA-256 checksum.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| LP-SPEC-013 | A release archive MUST contain `release.signed.json` first and then exactly its signed, sorted file list, including `manifest.json`, `main.mjs`, styles, workers, and traced assets. Verification MUST reject unsafe paths, extra files, hash or size changes, plugin-ID or version mismatches, and invalid signatures.                                                                                                                                                                                                                                                                                                                                                                                                |
| LP-SPEC-014 | Runtime bundling MUST externalize only approved declared Lapis host modules whose package roots are peer dependencies and the exact compiler-emitted `svelte`, `svelte/internal/client`, and `svelte/internal/disclose-version` renderer ABI. Those implicit Svelte imports MUST resolve from the host peer without becoming authored manifest shared dependencies; every other dependency MUST remain bundled. The runtime descriptor, package name, plugin ID, version, and source commit MUST be covered by the signed envelope. |
| LP-SPEC-015 | GitHub releases MUST use package-scoped tags such as `graph@0.1.0` and attach the archive and checksum produced from the matching package version. A bad published npm version MUST be superseded by a fixed patch and deprecated; unpublishing MUST NOT be the normal rollback. A corresponding GitHub tag MAY be removed only when it is not required by a registry publication.                                                                                                                                                                                                                                                                                                                                     |
| LP-SPEC-016 | Publication automation MUST remain manual and fail closed unless the first-publication gate is explicitly approved. It MUST use npm trusted publishing rather than a long-lived npm token, publish npm before public assets, and dispatch the verified repository, package, plugin ID, version, tag, asset, and source commit to the registry with a narrowly scoped GitHub App token. The installation token MUST be minted from the App client ID and private key.                                                                                                                                                                                                                                                   |
| LP-SPEC-017 | CI MUST run package boundary, App-ownership, native-CSS, unit, type, Svelte, build, publint, npm-pack, specification, release-security, deterministic archive, signature, shared Storybook, interaction, and accessibility gates. Clean registry-only Web and Deno runtime acceptance MUST complete before first publication.                                                                                                                                                                                                                                                                                                                                                                                          |
| LP-SPEC-018 | Private signing material MUST enter automation only through encrypted secrets and MUST never be printed, committed, included in npm tarballs, or attached to a release. Local preparation MAY use an explicitly test-only ephemeral key.                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| LP-SPEC-019 | Published plugin packages MUST be directly consumable by supported Vite hosts without package-specific aliases or dependency-optimizer exceptions. Browser workers MUST use package-stable emitted paths and a standards-aligned module-worker constructor.                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| LP-SPEC-020 | The shared Storybook and browser-test project MUST pre-bundle deep Mira modules and transitive CommonJS dependencies of excluded framework source while keeping `@lapis-notes/api` deduplicated. Plugin stories MUST share API-owned application and workspace state instead of embedding private state in optimized plugin chunks. Shared real-App fixtures MUST wait for explicit readiness with bounded allowance for concurrent catalog startup.                                                                                                                                                                                                                                                                   |
| LP-SPEC-021 | Every plugin package MUST own a schema-versioned `registry.json` containing curated categories, bounded plain-text highlights, optional HTTPS documentation, and safe relative Overview and Changelog Markdown paths. Package metadata checks MUST verify all twelve source files and MUST reject unsafe paths, missing content, unsupported fields, insecure links, or Markdown over 256 KiB.                                                                                                                                                                                                                                                                                                                         |
| LP-SPEC-022 | Plugin source metadata MUST NOT claim registry badges or trust. Name, description, author, version, and compatibility MUST remain manifest-owned; license, homepage, repository, and issue links MUST remain package-owned. Registry automation MAY derive those fields only after verifying plugin, package, repository, and exact source-commit ownership.                                                                                                                                                                                                                                                                                                                                                           |
| LP-SPEC-023 | Metadata-only registry dispatch MUST carry only repository, package name, plugin ID, and full source commit. It MUST use the same narrowly scoped registry credential as release dispatch and MUST NOT publish npm, create release assets, or change a plugin version.                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| LP-SPEC-024 | The repository MUST commit its root pnpm lockfile. CI and approved-release workflows MUST install that exact dependency graph with `--frozen-lockfile` before building, testing, signing, packing, or publishing any plugin artifact.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| LP-SPEC-025 | The manual release workflow MUST expose one boolean selection for every first-party plugin, default every selection to enabled, reject an empty selection, and pass only the resolved explicit package list to publication. It MUST NOT require operators to type package or plugin identifiers into a free-form field.                                                                                                                                                                                                                                                                                                                                                                                                |
| LP-SPEC-026 | A same-version replacement MAY overwrite only the matching GitHub release archive and checksum after an explicit plugin selection, matching npm integrity, and proof that the registry does not publish that version. It MUST NOT overwrite, unpublish, or republish npm; a registry-published defect MUST use a fixed patch and npm deprecation.                                                                                                                                                                                                                                                                                                                                                                      |
| LP-SPEC-027 | GitHub CI and release workflows MUST configure Node 24 LTS and use action majors whose JavaScript entrypoints run on Node 24, so repository automation does not depend on GitHub's deprecated Node 20 action runtime. Both workflows MUST install the pinned mdBook tool required by the canonical specification gate before release preparation.                                                                                                                                                                                                                                                                                                                                                                      |
| LP-SPEC-028 | Full all-plugin release preparation MUST remove stale generated plugin archive directories before signing the current twelve-version candidate set. A focused single-plugin build MAY preserve other current candidates, but verification of the full set MUST never scan archives produced by a prior signing key or version.                                                                                                                                                                                                                                                                                                                                                                                         |
| LP-SPEC-029 | Release versioning MUST preserve Changesets-generated package history and append the candidate entry. Documentation synchronization MUST NOT regenerate or overwrite package `CHANGELOG.md` files.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| LP-SPEC-030 | Every first-party `registry.json` MUST define an allowlisted semantic icon and six-digit accent colour. It MAY define a square logo under `registry-assets/`; the package audit MUST reject unsafe paths, missing assets, unsupported image formats, unsafe SVG content, and invalid dimensions. Registry automation MUST hash and mirror supplied logos, and clients MUST retain the icon-and-accent fallback.                                                                                                                                                                                                                                                                                                        |
| LP-SPEC-031 | Every first-party plugin MUST provide one to five deterministic 3:2 registry cards under `registry-assets/`. Each card MUST declare one fixed Storybook story, bounded alt and marketing copy, an allowlisted text palette and crop, and the four themed outputs governed by LP-SPEC-042. Governed source stories MUST remain under the owning plugin's `Registry Screenshots` section with `registry-media` and `visual-pending` tags. |
| LP-SPEC-032 | Every first-party manifest MUST declare `isDesktopOnly` explicitly. Release compatibility MUST use only `web` and `desktop`: desktop-only plugins emit `desktop`, while portable plugins emit both values. Electron runtime-host terminology MUST NOT appear as a registry platform.                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| LP-SPEC-033 | Every first-party `registry.json` MUST source its Overview from `registry-content/overview.md`. The Overview MUST describe end-user plugin behavior and MUST NOT include package-manager installation or static-composition instructions; package READMEs remain the source for developer integration.                                                                                                                                                                                                                                                                                                                                                                                                                 |
| LP-SPEC-034 | The shared Storybook interaction gate MUST treat Svelte's `derived_inert` runtime warning as fatal whether it is emitted through `console.warn` or `console.error`, while leaving unrelated diagnostics unchanged. The warning classifier MUST have focused regression coverage and the browser suite MUST exit non-zero whenever the warning is observed.                                                                                                                                                                                                                                                                                                                                                             |
| LP-SPEC-035 | Until every resolved Bits UI version ships equivalent upstream teardown behavior, the workspace MUST apply tracked pnpm patches that cancel Link Preview's deferred selection probe and Scroll Area's deferred resize work before their owning Svelte effects are destroyed. The patch mapping MUST cover every Bits UI version in the lockfile and release tests MUST fail if the mapping or either lifecycle correction is removed.                                                                                                                                                                                                                                      |
| LP-SPEC-036 | CI MUST consume the public multi-architecture `lapismd/lapis-ci` toolchain by immutable digest and MUST build a separate `lapis-plugins` dependency image whose tag is derived from the committed pnpm lockfile. The dependency image MUST contain only the fetched pnpm store from workspace manifests, patches, and the lockfile; it MUST NOT contain repository source or reusable `node_modules`. Publication MUST emit provenance and an SBOM, then open or update an idempotent PR that records the immutable image digest. Turbo remote-cache artifacts MUST be signed, use bounded timeouts, receive credentials only at runtime from organization Actions settings, and degrade to normal task execution when credentials or the cache service are unavailable. Workflows MUST NOT use GitHub Actions cache storage for `.turbo`. |
| LP-SPEC-037 | Package CI MUST schedule `build`, `check`, and `test` through one Turbo graph. Its default concurrency MUST be half the available processors with a minimum of one and maximum of four, while accepting an explicit numeric or percentage `TURBO_CONCURRENCY`. Standalone npm packing MUST build first, while release preparation MUST reuse the already validated build. Tarball work MUST use at most four workers and plugin runtime bundling at most two; both worker pools MUST stop scheduling queued work after failure and MUST sort results before writing manifests or logs so output remains deterministic. The repository MUST provide a digest-pinned local container runner with lockfile-keyed pnpm-store, root/package `node_modules`, and `.turbo` volumes, and MUST forward remote-cache setting names without embedding secret values. |
| LP-SPEC-038 | GitHub CI MUST populate package build outputs once, then run quality, unit, static Storybook, interaction/accessibility, and release-artifact jobs concurrently in the digest-pinned dependency image. Every clean job MUST explicitly trust the checked-out workspace for read-only Git metadata discovery, perform the normal frozen install, and restore package builds through the signed remote Turbo cache when available. Cache misses, fork pull requests without secrets, and cache-service failures MUST execute tasks normally. One stable `validate` job MUST fail unless every functional lane succeeds; Visual Delta capture and pending baseline work MUST remain non-blocking. Workflow concurrency MUST cancel superseded branch and pull-request runs, and candidate artifacts MUST be uploaded only by the release-artifact lane after archive verification. |
| LP-SPEC-039 | Manual publication MUST first call the same reusable blocking CI workflow, then build a production-signed candidate in the digest-pinned dependency image. The candidate job MUST upload only verified npm tarballs, plugin archives, checksums, the public verification key, and an exact-source release plan. A separate protected-environment publication job MUST download that candidate, reverify every signature, checksum, package coordinate, source commit, and release-plan byte before npm, GitHub release, or registry mutation. The selected plugin list and same-version GitHub-asset replacement choice MUST remain explicit across that boundary, and the workflow MUST NOT rebuild release payloads after candidate download. |
| LP-SPEC-040 | The shared Storybook host MUST compile Design Core's catalog stylesheet so DM Sans Variable and Source Code Pro Variable resolve in the browser. It MUST expose the brand-theme selector and light/dark toolbar control and apply both globals to the preview document. Browser-only dependency shims MUST preserve production named exports, including Harper's inlined `binary` value. Registry capture MUST wait for both fonts and request the declared Lapis light or dark presentation. |
| LP-SPEC-041 | Every first-party manifest MUST declare the HTTPS Lapis author avatar for `dev@lapis.md`. Manifest auditing MUST reject a missing, insecure, or different first-party avatar without changing package identity or release provenance. |
| LP-SPEC-042 | Every first-party registry source MUST declare banner media plus one to five gallery items and MAY declare one Overview image only for a materially different full-screen state. A declared Overview MUST use a different governed story from the banner. Each item MUST expose a 1200x800 split preview and 2400x1600 split, light, and dark lossless-WebP outputs. Capture and card instructions MUST remain source-only. |
| LP-SPEC-043 | Registry capture MUST render each distinct story once per light and dark theme at a 1200x800 CSS viewport and 2x density, cache by story and theme, and apply an exact corner-to-corner dark-upper-left/light-lower-right diagonal over half of the affected product area. It MUST reject stale, upscaled, malformed, or mismatched outputs and MUST NOT create or approve Visual Delta baselines. |
| LP-SPEC-044 | Full-workspace Autodocs families, including registry-media stories, MUST use the shared padding-free Docs canvas and render each story in an isolated 700-pixel-high iframe. A repository-local specification audit MUST inventory these families and fail when a story omits the shared contract. |
| LP-SPEC-045 | Autodocs stories rendered through a Storybook-only demo, harness, or fixture MUST provide complete `docs.source` metadata with copyable public package usage. The canonical specification validator MUST reject missing source fields and source that exposes demo, harness, fixture, or Storybook `args` boundaries. |
| LP-SPEC-046 | Governed component Autodocs MUST identify the actual public component, provide non-empty component and story descriptions, and expose only that component's public properties. Injected application objects MUST remain documented but non-interactive, and story-only harness properties MUST NOT appear in Properties. A repository-local audit MUST fail closed on omissions or component drift. |

Plugin behavior corrections use an independent package patch changeset and
retain focused owning-package checks plus real consumer Storybook acceptance as
release evidence. Preparing that candidate does not authorize npm publication,
public release assets, or registry dispatch.
Registry media refinement MUST preserve the fixed story IDs and output
dimensions while strengthening each story's final-state assertions. Shared
fixtures MAY stabilize source-specific diagnostics after the real provider has
produced them, but MUST keep the editor and Problems collections consistent.
Applying that changeset to a release candidate MUST update the selected package
metadata and each owning plugin chapter together, then pass the complete
tarball, signed-archive, and clean-consumer preparation gate before approval.
